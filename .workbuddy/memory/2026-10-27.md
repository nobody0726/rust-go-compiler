## 结论（一句话）

**「真 live-in 位图让四个语料全坏」的根因不在位图，在 `rt_defer_push`。**

```text
MakeClosure ──► 闭包块分配，写 dst 槽
Defer       ──► bl rt_defer_push(fp, fv)
                  └─ rt_arena_alloc ──► gc_alloc(K_ARENA)
                                          └─ stress 钩子在**分配之前**跑 GC
                                             ① 新 DeferRec 还没挂 g_defer_top
                                             ② Defer 不是 safepoint
                                                ⇒ sp_idx 停在 MakeClosure 位点
                                             ⇒ 闭包块的唯一根 = 那张位图
```

超集恰好含 `MakeClosure` 的 dst ⇒ M10 一直没露（**巧合**）。
真 live-in ⇒ 闭包被回收 ⇒ 堆地址被下一个闭包复用 ⇒ `rt_deferrun` 调到
**别人的**闭包 ⇒ panic 且 `recover()` 救不回来。

## 修法

`rt_defer_push` 加 `gc_pause`（`C12` §6.1 / `R-10-24`），与 `rt_alloc_escaped`
同源（一次分配 + 立即发布）。守卫 `t_gc_12` 断言顺序
`gc_pause++` < 分配 < `g_defer_top = r;` < `gc_pause--`。

**位图仍保留 live-out 超集** —— 策略选择（代价不对等），不是给缺口打补丁。

## 三个坑（都写进 rt.c 注释）

1. **`gdesc` 不能用 `rt_arena_alloc`** —— `rt_init` 会调它，走 arena 就等于在
   `_start` 里触发第一次 `rt_grow`（16 MiB mmap），「空程序只在第一次分配时
   才 mmap」这条 M10 的惰性行为变了 ⇒ `allocs`/`heap` 读数全偏移。
   改用**静态数组** `g_descs[1024]`（64 KiB `.bss`，不进文件、不占物理页）。
2. **链接必须 `-no-pie`** —— PIE 下全局符号不能用 `adrp + :lo12:` 直接寻址
   （`relocation R_AARCH64_ADR_PREL_PG_HI21 … can not be used when making a
   shared object`），而 `rt_switch` 自测要直接引用全局。产物本来就没动态段。
3. **自测函数自己必须守 ABI（`R-11-1`）** —— `rt_sc_run` 往 18 个 callee-saved
   里填值，不先保存 C 的那份 ⇒ 返回时踩烂调用方（`rc=139`），而现象**看起来
   像 `rt_switch` 切坏了**。查了五轮 `brk` 二分才定位到「不是被测对象的问题」。
   **教训**：判据红了先分辨「被测对象错」还是「探针自己错」—— M10 的六次假绿
   是后者的另一个形态。

顺带：六个判据骨架的 fixture 全部缺 `package main`（`#[ignore]` 掩盖了，
`t_stk_01` 一启用就露）。

## Task 10（序言栈检查）· 同日稍晚

commit `42f9195`。**本地领先 origin 3 个 commit，push 一直失败**
（`Failed to connect to github.com port 443`，75 s 超时；`gh api` 通 ⇒ 是 git
这条路不通，不是断网）。⚠️ **`timeout N git push | tail` 的退出码是 `tail` 的**，
不能用它判断成败 —— 要用 `git status -sb` 看 `领先 N`。

### 三个实测修正（都写进注释）

1. **`stack_lo = sp - 8 MiB` 来不及** —— 正好在栈底之外，进程先踩 guard page
   ⇒ `rc=139` 而不是 `rc=2`。改 **4 MiB**（留一半余量）。
2. **溢出文本的 `<N>` 必须动态算**（`g_cur->stack_hi - stack_lo`），写死 65536
   会让 `main`（进程栈 4 MiB）的溢出报一个假数字。判据 `T-STK-03` 断言的正是
   「文本与真实限制一致」。
3. **两个 `u64 *` 相减是按元素个数算的**（C 指针算术）⇒ 把 4 MiB 报成 512 KiB。
   必须先转 `u64`。

### 判据

`t_stk_03`（rc=2 + `goroutine stack exceeded 4194304 bytes`）/ `t_stk_04`
（`cmp sp, x9`、`b.hs .Lso_`、`bl rt_panic_stack_overflow` 三条数相等 ——
只查「有检查」不够，要成对）/ `t_stk_05`（`nilptr2` 不误报 + 检查条数 < 函数数）。
`t_stk_06` 推到 Task 12（要在 64 KiB 的新 G 上测）。

**装置坑**：`native_harness::build_and_run_env` 把「退出码非 0」当错误 ——
而栈溢出**就是** rc=2。`go_stack.rs` 里另写了 `build_then_run`（直接
`run_build` + `Command`）。
