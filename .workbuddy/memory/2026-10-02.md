### 从源码读出的五条 harness 必需规则（`M0-tests.md` §1.3，均带源码行号）

1. **指令行提取**（`:502-515`）：跳过 `//go:build` / `// +build`，取「首个非空且非构建约束的行」→ **不能假定指令在第 1 行**；找不到则 `Fatalf`
2. **输出期望**（`:1169-1193`）：**`.out` 缺失 ⇒ 期望输出为「空」**，而非「任意输出均可通过」；比较前 `\r\n`→`\n` 归一化；严格相等；报错措辞分「内容不符」与「本应为空却非空」两种 —— **这推翻了之前的猜测**
3. **诊断切分**（`:1195-1213`）：`\t` 开头为续行；跳过 `go tool` / `#` / `<autogenerated>` 开头与空白行
4. **ERROR 解析**（`:1432-1499`）：`errRx = // (?:GC_)?ERROR (.*)`（也支持 `GC_ERROR`）；**一行可有多个引号模式**（故 `mainsig.go` 同行两条）；含 `////` 的行跳过；`LINE±n` 替换为 `文件:行号`；模式编译为**正则**
5. **裸 `// errorcheck` 也会被自动追加 `-d=ssa/check/on`**（`:613-625`）→ 印证 `03` §3.1「errorcheck 期望不能当纯语言语义验收」

## 追加：CodeLLDB「无法下载」结案 + T28 调试目标形状修正

用户报「vscode dev container 中打开时，报错无法下载 CodeLLDB」。查清了，并且连带发现一个 T28 的计划缺陷。

### 一、CodeLLDB 平台包缺失（真因与之前推断不同）

**关键区分**：CodeLLDB 拆成两部分 —— ① 扩展**本体**（marketplace）；② **平台包**
`codelldb-<platform>.vsix`（GitHub releases，含真正的 lldb 二进制）。① 装成功不代表可用；
② 才是断点能不能工作的前提。判据：`<扩展目录>/platform.ok` 与 `<扩展目录>/lldb/bin/lldb`。

**根因（6 条证据，已坐实）**：宿主 VSCode 通过 AHP `root/configChanged` **主动把**
`http.proxy = http://127.0.0.1:7897` **下推进容器**（证据在
`~/.vscode-server/data/logs/<会话>/ahp/ahp-*.jsonl`）。容器内 `127.0.0.1` 是容器自己的 loopback。

**⚠️ 推翻了上一轮的结论**：之前以为「写进远端 Machine settings 的 `http.proxy: ""` 优先级高于
User settings，故能覆盖」。**实测不成立** —— Machine settings 写入时间 03:31:58，之后新开的会话
03:40:12 **仍报同一错误**。因为该值由**客户端**下发，远端机器级设置排不上队。
（devcontainer.json 里那两行予以保留，但已明确标注「不是修法」。）

**修法**：`scripts/install-codelldb.sh` —— `curl --noproxy '*'` 直连下载 + 用 VSCode 自带的
`code-server` CLI 从本地 vsix 安装（`remote-cli/code` 不行，它要求 `VSCODE_IPC_HOOK_CLI`）。
实测：下载 HTTP 200 / 54,544,514 B / 13–30 s / 4.1 MB/s；安装成功；断言 `lldb version 22.1.8-codelldb`。
幂等（`platform.ok` 短路）；容器重建后重跑即可（`~/.vscode-server` 不在卷里，重建会清空）。

**同一死代理还打坏 GitHub / Copilot 扩展**（`connect ECONNREFUSED 127.0.0.1:7897`），本仓不依赖它们。

**顺带修正两处事实**：
- 调试器用的是平台包**自带**的 `lldb 22.1.8-codelldb`，不是镜像里的系统 `lldb 14.0.6`；
- 非 root 用户跑时 `/proc/self/status` 的 `CapEff` **恒为 0**，不能用它判断容器能力 ——
  要 `docker inspect`（实测 `CapAdd=["CAP_SYS_PTRACE"]`、`SecurityOpt=["seccomp=unconfined"]`，本来就对）。
  原 T28 的排障建议写的就是错的命令。

### 二、T28 的调试目标形状有缺陷（计划缺陷 #8）

原目标：`pub fn add(a,b) -> i64 { let sum = a + b; sum }`，T28 第 4 项要求「F10 单步后看到 `sum == 3`」。

**实测：`sum` 根本不在 DWARF 里。** `add` 的 subprogram 子节点只有形参 `a`、`b`，
没有 `DW_TAG_lexical_block` / `DW_TAG_variable sum`，且 `<2094> Abbrev Number: 0` 明确结束子节点。
→ **任何**调试器（lldb CLI / CodeLLDB / gdb）都看不到它，这一项**不可实现**。

**对照实验**（同 crate、同 profile）：

| 形状 | DWARF 里有 `sum`？ |
|---|---|
| `let sum = a + b; sum` | ❌ 无 |
| `let sum = a + b; sum * 2` | ✅ 有（lexical_block → variable） |
| `let sum = a + b; let doubled = sum * 2; doubled` | ✅ 有 |

**规则**：尾位置直接返回的 `let` 绑定被 rustc 与返回值合并，不生成变量条目；
被**第二次读取**才生成。环境：rustc 1.98.1 / unoptimized + debuginfo / aarch64。

**修正**：调试目标改为 `double_sum(a,b) -> i64 { let sum = a + b; sum * 2 };`（断言 `double_sum(1,2)==6`）。
副作用：① `sum * 2` 作尾表达式**不再触发 `clippy::let_and_return`**，那句 `#[allow]` 已删除
（T22 门禁在无 allow 下 exit=0）；② 断点行 21 → **27**。
