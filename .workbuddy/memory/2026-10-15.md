## ⚠️ 本轮的三个关键发现（都已写进 ledger Rulings）

1. **`expr()` 的二元运算符判据少了 `form == Plain` —— T-AP10 遗留的真 bug，代码注释写反了**。
   `binary_op_here` 原来是「`TokenKind::Op` 且 `tprec > prec`」，注释断言「`+=`/`++` 的优先级都是 0」——
   **错**：`+=` 是 `(Assign, Add)`、`++` 是 `(IncDec, Add)`，`op` 都是 `Add` ⇒ `prec == 4`，与 `+` 一样
   （M1 契约：`prec` 只按**语义运算符**取值，`test_token.rs:156`）。⇒ `x += 1` 被读成 `Binary(Add,x,1)`、
   `i++` 被读成二元 ⇒ `for i := 0; i < n; i++ {}` 报 `expected expression`，**报错指在 `++` 后面那个词元上**，
   看起来像「`simpleStmt` 没认 `_IncOp`」——极易归因错。附带结论：`simpleStmt` 路径一的
   `_AssignOp`/`_IncOp` 两条臂在此之前是**不可达的死代码**。
   **防御手段**：判据写 `form: OpForm::Plain`（= 官方的 `_Operator || _Star`）；`prec` 是 `u8`，
   **类型上装不下 `form`**，不能替代。
2. **`IfStmt.cond` 可以是 `nil`（同形第 3 次）**：官方 `header` 的具名返回值 `cond` 在 `if x y {}` 那条
   恢复路径上**从不被赋值**（`want(_Lbrace)` 报错 → `advance` 恰好停在 `{` ⇒ `else if p.tok != _Lbrace`
   不成立 ⇒ `condStmt` 保持 nil、`semi` 也没记）。⇒ 改 `Option<Expr>`。
   **与 PA-1 / `Op::Tilde` 不同之处**：那两次是"字段/变体少了"，这次是"某条**错误恢复路径**上字段保持零值"
   —— 只有把官方每条出口都走一遍才发现。**验收纪律加一条**：建模类任务的 diff 对象要包含
   **字段的可空性与零值可达性**，不只是字段列表。
3. **RF1 的端到端用例必须把两条语句分两行**：`if x == T{} { f() }`（同一行）是**非法 Go** ——
   官方 `stmtList:2726-2730` 在两语句间要 `;`，缺失时 `advance(_Semi,_Rbrace,_Case,_Default)` 会
   **一路冲到后面那个 `}`** 把 `{ f() }` 整块吞掉 ⇒ 树里只剩 1 条语句（与"少了 `xnest=-1`"**同形**）⇒
   用例失去分辨力。**实测**：同一行输入下我们输出恰好两条诊断（`at end of statement` +
   `non-declaration statement outside function body`），与官方恢复语义逐字吻合 ⇒ 证明**实现对、用例错**。
   改成 `if x == T{}\n{ f() }`。

## ⚠️ 本轮踩到的新方法论坑

1. **RED 的 22 条失败里 20 条是"断言写错"**（`syntax error: ` 前缀 12 条 / 对二元条件误用 `name_of` 3 条 /
   列号笔误 / 我留的临时 `panic!` 占位 1 条）。**这不是 RED 没用** —— 剩下 2 类是真缺口（上面第 1、2 条），
   而它们**只有先写测试才照得出来**。⇒ 先写测试的收益 = 这 2 条。
2. **`cargo check` / `cargo clippy` 打印的是 `Checking`，不是 `Compiling`**。用 `grep -c "Compiling"`
   去核对"有没有重编译"会得到 0，从而误判成"复用了旧产物"。修法：核对时同时 grep
   `Compiling|Checking`，或直接看 `Finished` 前面那几行。**这是本仓容器纪律里的一个新细节。**
3. **`collapsible_if` 在 `-D warnings` 下会打爆 clippy 门禁**：官方源码是**嵌套 `if`**（为了逐行同形），

官方 `p.want(tok)` 只有**一个**参数、名字由 `tokstring(tok)` 派生。我们早先是
`want(&Follow, &str)`，30 个调用点各自手写 ⇒ **大部分都错**：

| 我们写的 | 官方实际 | 差 |
|---|---|---|
| `expected ;` | `expected semicolon or newline` | `tokstring(_Semi)` 的第二特例 |
| `expected chan` | `expected keyword chan` | `tokstring` 的关键字前缀 |
| `expected for` / `if` / `switch` | `expected keyword for` … | 同上 |
| `expected ]` / `)` | 相同 ✓ | — |
| `expected closing delimiter` | `expected )` / `]` | `list` 那处自己写的占位 |

**症状**：语法完全正常，消息里几个字符不同 ⇒ 要到 `T-AP18` 对撞才暴露。

⇒ **纪律：一个函数的「描述性参数」若由调用方各处手写，就一定会在某处写错**；
把它收回到函数内部派生。

## 官方 `token.String()` 的 47 项对照表：**必须用脚本算**

我第一次**手数** `_token_index`，得到 46 个 token 对 48 个索引 ⇒ **整张表全错**
（`_Comma` 算成 `:`、`_Semi` 算成 `.`）。
改成「`re` 从 `token_string.go` 抽 `_token_name` + `_token_index`，按官方
`String()` 的公式 `_token_name[_token_index[i-1]:_token_index[i]]` 逐项算」
⇒ 47 项（46 token + `tokenCount`）全对。

⇒ **凡是从「生成的代码」里读数据，用脚本算，别用眼睛数。**

## 一个反直觉但**正确**的输出：`++` 的 `tok` 是**一个** `+`

`x ++ ++ 1` 的第二个 `++` 作为当前词元走 `_IncOp` 分支，官方是
`p.op.String()` —— 而 `++` 的 `op` 是 `Add` ⇒ 消息是
`syntax error: unexpected + at end of statement`（**一个 `+`**）。
官方 `operator_string.go` 印证：`Operator` 里**没有** `IncDec` 变体。

⇒ 这条同时说明 `_IncOp` 与 `_Operator` 的输出**在 `++` 上完全一样**
（都是 `+`）—— 只有 `_AssignOp`（`+=`）才多一个 `=`。
**这三条必须各有一条「当前词元真的是它」的用例**，否则「三档」照不出来。

## 一个**把 8 条用例一起带走**的死循环（症状极具误导性）

官方 `branches.go:186-202` 是 `for _, fwd := range fwdGotos`
（**遍历副本**，长度固定）+ `else { fwdGotos[i] = fwd; i++ }` 原地压缩
+ `fwdGotos = fwdGotos[:i]` 截断。我直译成：

```rust
while i < fwd_gotos.len() { if 匹配 { /* 不动 i */ } else { fwd_gotos[i] = fid; i += 1; } }
```

⇒ **匹配时不递增 `i`、`len()` 也不变 ⇒ 条件恒真 ⇒ 死循环**。

**症状**：不是报错，而是**内存被撑爆后被 SIGKILL（OOM）**，
而且**只在含 `goto` 的 8 条用例上出现** ⇒ 看起来像「`goto` 一律坏」。

⇒ **纪律：Go 的 `range` 遍历副本这个「隐含的快照」，在直译成索引循环时
必须显式造出来**（`let snapshot = v.clone();`）。

## 变异 runner 的一个新坑：命令**必须走 `in-container.sh`**

新写的 runner 用 `subprocess.run(cmd, shell=True)` 直接跑 `cd /work/rgoc && cargo …`。
`/work/rgoc` **只在容器里存在** ⇒ 宿主上**每条命令都静默返回空输出**。
下游看到的是「没有 `Compiling` 行」⇒ 报「cargo 复用了旧产物」，
而**真因是「命令压根没跑」**。

⇒ 这正是「静默失败」家族的成员：**命令失败与命令成功在下游同形**。
读前一轮的 runner（`runner_tap13.py` 的 `_container`）才发现该走
`["scripts/in-container.sh", "bash", "-lc", script]`。

**同时**：`touch lib.rs` 之后 cargo **仍可能**判定「源码没变」而复用旧产物
⇒ 必须先 `cargo build --workspace --tests` 强制走编译路径，再看 `Compiling` 行。

## 反向验证照出**两条恒真断言**（本仓第 7、8 次）

`t_a_66_name_的_tok_不是_裸_name` 与 `t_a_66_literal_的_tok_不是_裸_literal`
原来的写法是：

```rust
if m.starts_with("syntax error: unexpected name ") {   // ← 带**空格**
    assert_ne!(m, "syntax error: unexpected name, …"); // ← 裸 name 后是**逗号**
}
```

丢掉字面原文后的消息是 `unexpected name, …`（**逗号**）⇒ **前置条件不成立**
⇒ **整段断言被跳过**、测试照绿。

⇒ 修法：改成**无前置条件**的全称断言（`!m.contains("unexpected name,")`）。
⇒ **纪律：「反向验证」这类用例的前置条件必须与被测行为**独立**；
一旦两者相关（都在看同一个前缀），它就退化成恒真。**

### 一条新的纪律

**「反向验证」用例写不出判据时，正确做法是删掉它并写下「为什么写不出」，
而不是硬凑一条恒真断言。** 本仓已抓 6+ 次恒真断言 —— 硬凑第 7、8 次的成本更高。

分隔）⇒ 任何「按分隔符切 `<tok>`」的写法都会把字面切掉。要断这件事只能**逐字比对**。
