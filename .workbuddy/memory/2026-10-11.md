
**go1.27.1 实测输出（`sample.txt` = `package main\n\nfunc main() {\n\tprintln("hello")\n}\n`）**：

```
 1:1   package   "package"      ← 无字面量，lit 是关键字原文
 1:9   IDENT     "main"
 1:13  ;         "\n"           ★ 补出来的，源码无此字符
 3:1   func      "func"
 3:6   IDENT     "main"
 3:10  (         ""             ← 分隔符 lit 恒空
 3:11  )         ""
 3:13  {         ""
 4:2   IDENT     "println"      ← 只是 IDENT，M1 不认识内建
 4:9   (         ""
 4:10  STRING    "\"hello\""    ← lit 带引号，未解码
 4:17  )         ""
 4:18  ;         "\n"           ★ 补出来的
 5:1   }         ""
 5:2   ;         "\n"           ★ 补出来的
 5:3   EOF       ""
```

两条必须记住的实测事实：
1. **`/tmp/.../hello.go` 与 `dump.go` 同包会 `main redeclared`** —— 样本文件不能叫 `.go`
   放在同目录（改名 `sample.txt` 即可），这是 Oracle adapter 的一个坑。
2. **中文标识符验证字节列**：`\t变量 := 1` 实测 `变量@4:2`、`:=` @**4:9**（变量占 6 字节）——
   若按 rune 计数会得 4:6。✅ 直接坐实 C1 §2.1「col 是字节列」。

### 标识符切分机制（实测，`tok.go` 批量跑 12 个边界输入）

**机制不是「先找词尾再切」，而是「边走边问还能不能继续」，停下时那个字符【不消费】**
（`s.ch` 保持为终止符，`segment()=buf[b:r-chw]` 天然把它排除）——
这就是 Go 的 `nextch` 不需要回退的原因（唯一回退 `rewind()` 只服务 `..`）。

实测边界（go1.27.1）：

| 输入 | 输出 | 关键点 |
|---|---|---|
| `str1` / `str1x` / `str_` / `str2é` / `日本語` | 单个 IDENT | 续接字符集 = 字母 ∪ 数字 ∪ `_` ∪ Unicode 字母 |
| `str x` / `str+x` | `str` 与 `x` 分开 | 空格/`+` 停止且不消费 ⇒ 成为下一词元起点 |
| `for` | 关键字 `for` | **先切完整标识符，再查完美哈希** |
| `forx` | IDENT `forx` | ⇒ 证明关键字不是边扫边匹配的 |
| `1str` | `INT "1"` + `IDENT "str"`，**无词法错误** | `number()` 遇 `s` 即停，相邻合法性是 parser 的活 |
| `_x` | IDENT | `_` 属字母类（LEX-02） |

⇒ **「完整」是被谓词定义出来的，不是被检查出来的**：`isLetter||isDigit||_` 这个谓词的补集
就是合法的后继字符集。谓词写松/写紧 ⇒ 词元直接错，且**没有任何运行时检查会报警**。

### 通用语言澄清（含一条实测抓到的静默陷阱）

**核心区分：`tok` 回答「它是什么」，`lit` 回答「它长什么样」。**

实测（把官方 `scanner.go`/`source.go`/`tokens.go`/`token_string.go` 四文件复制成独立包跑，
在 `/tmp/rgoc-m1-demo/syn/`，可用 `go test ./syn -run TestDump -v` 复现）：

| 输入 | 输出 | 关键点 |
|---|---|---|
| `for i := 0` | `for` 的 `lit=""`；`:=` 的 `lit="i"` | ⚠️ **关键字不设 lit**（`ident()` 命中关键字后直接 `return`，跳过 `s.lit=`）；分隔符的 lit 是**上一个词元的残留** |
| `a, b := 1, 2` | `,` 的 `lit="a"`、`:=` 的 `lit="b"` | 同上 —— **不是空值，是陈旧值**，naive 读它会拿到上一个 token 的文本还以为是自己的 |
| `1.5e3i` | `kind=2`（ImagLit）`bad=false` | LitKind: 0=Int 1=Float 2=Imag 3=Rune 4=String |
| `a >>= 2` | `op=>> prec=5`（tok 是 `_AssignOp`） | **op/prec 与 tok 是两个维度**：同一 `>>=` 的词元类别是"复合赋值"，操作符是 `>>` |
| `;`（行尾补的） | `lit="newline"`；EOF 补的 `lit="EOF"`；显式 `;` 的 `lit="semicolon"` | 三处赋值点 `scanner.go:121/154/113` |

⇒ **「literal」一词在本仓有 4 个不同所指**（必须分开）：
①上下文里的"字面量"= 源码文本单元；②`_Literal` = 词元**类别**；
③`LitKind` = 字面量的**子类别**；④`lit` = **字段名**，存任意词元的原文切片。
⇒ 结构体注释原文就是判据：`lit` **valid if tok is _Name, _Literal, or _Semi`**，其余时候无效。
⇒ 这正是本仓反复踩的「静默失败」形状：**字段有值、类型合法、语义是错的**。

### ⚠️ 官方有【两个】词法器，粒度不同 —— 必须先选一个当基准

| | `src/go/scanner/`（公开 API） | `src/cmd/compile/internal/syntax/`（编译器用） |
|---|---|---|
| 数字字面量 | `token.INT` / `FLOAT` / `IMAG` 三个独立类别 | 一个 `_Literal` + `LitKind` 子类 |
| 字符/字符串 | `token.CHAR` / `token.STRING` | 同上，靠 `kind` 区分 RuneLit/StringLit |
| 位置 | `token.Position{Filename,Offset,Line,Column}`（Line/Column 1 起） | `Pos{base,line,col}`，base 是 `*PosBase` 指针 |
| 分号 | `token.SEMICOLON`，不需要就不看 lit | `_Semi` + `lit` ∈ {semicolon, newline, EOF} |

**本仓基准是编译器那个**（`01-feature-set.md` PIPE-02 指向 `gc/syntax/scanner.go`）。
⇒ **通用语言必须跟编译器版**：说"字面量"时它是**一个类别 + 一个子类字段**，
不是 `INT`/`STRING` 这些独立类别。若拿 `go/scanner` 的输出去对 golden，粒度就对不上。
⇒ 与 C1 的真实差异：C1 的 `Pos.file` 是 **String**，官方是 **`*PosBase` 指针**（为了轻量 + `//line` 重映射）。
   M1 要不要引入 base 链 = 上轮列的开放问题 3。

### 词元结构体全字段实测（`syn/dump3_test.go` / `dump4_test.go`）

**结论：`tok + lit` 不足以描述一个词元。** 至少还要 `kind`（字面量子类）、`op`+`prec`（运算符类）、
`bad`（字面量有误），且**位置不属于词元字段而是另一组**。

官方 `scanner` 结构体里属于「当前词元」的字段共 **9 个**：
`line, col, blank, tok, lit, bad, kind, op, prec`（`mode, nlsemi` 属**扫描器状态**，不属词元）。

实测 `LitKind` 取值：**0=IntLit 1=FloatLit 2=ImagLit 3=RuneLit 4=StringLit**。
`bad` 语义实测（都仍产出 `_Literal` 词元，只是 `bad=true` + 一条诊断）：

| 输入 | kind | bad | 诊断 |
|---|---|---|---|
| `1` / `0123` | 0 | false | 无（`0123` 是合法八进制） |
| `1.5` | 1 | false | 无 |
| `0x` | 0 | **true** | hexadecimal literal has no digits |
| `1__2` | 0 | **true** | '_' must separate successive digits |
| `'ab'` | 3 | **true** | more than one character in rune literal |
| `"unterminated` | 4 | **true** | string not terminated |

⚠️ **`lit` 对分隔符/运算符/关键字是空的或陈旧的**（dump3 实测：`{` 的 lit 显示为上一个词元 `'x'`）。
⇒ 想知道分隔符/运算符的**源文本**，只能从 `tok`（分隔符）或 `op`（运算符，`_AssignOp` 要补 `=`）反推。
⇒ **词元的源文本散落在多个字段里，取决于类别** —— 这是 Go 用「扁平结构体 + 注释说明有效域」的直接后果。

### 🎯 对 M1 的 Rust 设计结论

**不要照抄 Go 的扁平结构体**（它是「胖结构体 + 注释约定有效域」，非法状态可表示）。
Rust 应当用 **和类型（enum）** 让「字段只在某类词元存在」由类型系统保证：

```rust
pub struct Token { pub pos: Pos, pub kind: TokenKind }

pub enum TokenKind {
    Ident(String),                                    // _Name
    Literal { text: String, lit_kind: LitKind, bad: bool },
    Keyword(Keyword),                                 // 25 个，独立枚举
    Op { op: Operator, prec: u8 },                    // _Operator/_AssignOp/_IncOp/_Star
    Delim(Delim),                                     // ( ) [ ] { } , : . ... ;
    Semi(SemiOrigin),                                 // Explicit / Newline / Eof
    Eof,
}
```

对齐关系：Go 的 `tok` 拆成 `TokenKind` 的**判别式**；Go 的 `lit` 变成**各分支的载荷**；
Go 的 `bad`/`kind`/`op`/`prec` 分别挂到对应分支里 —— **「有效域」从注释变成类型**。
另：`Pos` 独立成 VO（C1 已冻结），不塞进 `TokenKind`。

### 「oracle」概念澄清 + M1 的 token golden 三个现成来源（实测清点）

**oracle ≠ 语料。** oracle = **精确版本的参考实现**（容器内 `go1.27.1`，`oracle.rs` 顶部注释原文
"oracle 就是容器内精确的 `go1.27.1`"），作用是**回答"正确答案是什么"**；
`go_source_code/test/` 是**语料**（输入 + 人工写的期望注释）。两者是不同层，不能混。

三个层次：**语料**（输入）→ **oracle**（现场问答案）→ **golden**（把答案冻结存盘）。
golden 的意义：**冻结后不再依赖 oracle 也能回归**（E6 三次一致靠它）。

**M1 的 token golden 有三个现成来源**（清点结果）：

| 来源 | 规模 | 形态 |
|---|---|---|
| `syntax/scanner_test.go` 的 `sampleTokens` 表 | **133 条**（`_Literal` 48 / `_Operator` 20 / `_Name` 12 / `_AssignOp` 11 / `_Star` 1 / … 每关键字各 1） | `{tok, src, op, prec}` 四元组，`src` 即期望 `lit` |
| `go/scanner/scanner_test.go` 的 `TestNumbers` / `TestSemicolons` 表 | — | 数字与分号的状态表 |
| 语料 `test/syntax/semi1.go`…`semi7.go` + `test/{int,float,char,string}_lit.go` | 7 + 4 | `// errorcheck` 带 `// ERROR "..."` 注释 |

⚠️ `TestTokens` 的判据只有两条：`got.tok != want.tok` 与
`(tok==_Name||tok==_Literal) && got.lit != want.src` —— **它对运算符/分隔符不断言 `lit`**
（因为那些类别的 `lit` 本就无效）。**这是官方自己承认有效域的例子，M1 的测试照它写即可。**

**流水线五步**：语料 → adapter（专用小程序）→ **golden 冻结** → M1 Rust 输出 → 比对。

**关键纠正：对比的是 M1 ↔ golden，不是 M1 ↔ 活 oracle。** oracle 只在两处出现：
①生成 golden 时；②golden 对不上、需要判断「是实现错还是录错了」时回去复核。

**adapter 的三条规范化纪律（都是实测踩出来的）**：

1. **只录有效域内的字段**。第一版把 `lit` 无条件录进去 ⇒ `(` 的 lit 显示为上一个词元的 `main`，
   **等于把实现细节写进契约**（Rust 用 enum 后残留值必然不同 ⇒ 无意义红灯）。
2. **诊断与词元分两条流、各自排序**。第一版按「事件顺序」输出 ⇒ 诊断 `E 4:8` 出现在
   词元 `T 4:7` 之前，**golden 编码了「何时触发诊断」的内部时序**。
   改按 C1 §4 排序键（line→col→code）后固定在两组 `== tokens ==` / `== diags ==` 下。
3. **确定性**：不含地址/时间/随机序。实测同一输入 3 次 sha256 完全相同
   （`hello` = `a4115771…`，`bad_utf8` = `c7a0fdb7…`）。

**负例 golden 实测（`bad_utf8.txt` = `x := 1\xff2`）**：
词元流里 `4:7 literal lit="1\xff2"`（**非法字节留在字面量原文里**），
诊断流里 `4:8 invalid UTF-8 encoding` —— ⇒ **负例必须同时断言两条流**。
⇒ 另注：`lit` 是**原始字节切片**，可能含被报错并跳过的字节（BOM/NUL/非法 UTF-8 三种情况都已实测）。

## 官方如何处理注释（源码实测，决定 M1/M2 边界）

**结论：`cmd/compile` 看不见普通注释 —— 连文档注释也看不见。**
证据：`syntax/parser.go` 的 `newParser` 把 scanner 初始化成 **`directives` 模式**，
该模式下 `lineComment`/`fullComment` 只对 `//`(或 `/*`) 后紧跟 `g`/`l` 的注释才继续匹配
（`if s.mode&directives == 0 || (s.ch != 'g' && s.ch != 'l') { skip; return }`），
**其余注释在扫描器里就被跳过，从未进入 parser**。

`directives` 模式下真正被处理的只有两类：
1. **`//line`** → parser 的 `updateBase()`（**位置重映射在 parser，不在 lexer** ✅ 与 D-M1-1 一致）
2. **`//go:`** → ① `//go:build` 由 `constraint.Parse` 解析出 `GoVersion`（`-lang` 门控）
   ② 其余经 `PragmaHandler` 挂到最近的 package/import/const/func/type/var 声明上；
   落到语句等不接受 pragma 的位置会**退回并报 unused**（`clearPragma`）

**编译器认识的 `//go:` 指令全集**（`noder/lex.go` 逐条 `case`，共 15 条）：`go:build`、
`go:nointerface`（需 `goexperiment.FieldTrack`）、`go:noescape`、`go:norace`、
`go:nosplit`（隐含 NoCheckPtr）、`go:noinline`、`go:nocheckptr`、`go:systemstack`、
`go:nowritebarrier`、`go:nowritebarrierrec`（隐含前者）、`go:yeswritebarrierrec`、
`go:cgo_unsafe_args`（隐含 NoCheckPtr）、`go:uintptrkeepalive`、`go:uintptrescapes`、`go:registerparams`。
另有 `go:embed`（`noder/noder.go` 单独处理）与 `go:linkname`（导出侧）；
以及非 `go:` 前缀的 cgo 链接指令 6 条（`cgo_export_static/dynamic`、`cgo_import_dynamic/static`、
`cgo_dynamic_linker`、`cgo_ldflag`）。

**⚠️ 死代码发现**：`syntax/nodes.go` 里**有** `Comment`/`CommentKind`（4 种位置 Above/Below/Left/Right），
但 `printer.go` 与 `dumper.go` 中所有相关代码**全被注释掉**，且**没有任何代码构造 `Comment{}`**
⇒ 该类型在编译器里是**未使用的遗留**。`testing.go` 的 `CommentMap`/`CommentsDo` 只是
**测试辅助**（用来验证语料里的 `// ERROR` 注释），不是编译器主路径。
⇒ 对照：`go/parser` + `go/doc`（gofmt / go doc / vet）用 `ParseComments`，**保留全部注释**。
**同一个文件，编译器与工具链看到的注释是不同的。**

**对我们的阶段归属（与 `03` 既有规划一致）**：
M1 = 识别 + 上报（D-M1-1 的两种 mode），**不解析**；M2 = 消费（`//line` 重映射、`//go:build`
版本门控、pragma 挂声明、未知指令拒绝 —— 对应 `01` 的 PIPE-05/PIPE-04、AST-03）；
M3/M4 = 构建约束参与文件选择；M7+ = 个别 pragma 才有效果，**首发不承诺**（`03` §M2 原文）。

## ⚠️ 重大发现：Rust std 的字符分类**不能**用于 LEX-02（实测量化）

**LEX-02 要的是**：字母 = `Lu/Ll/Lt/Lm/Lo`；数字 = `Nd`。
**Rust std 只能给**：`char::is_alphabetic()` = Alphabetic 属性（含 **Other_Alphabetic**）；
`char::is_numeric()` = `N*`（Nd+Nl+No）。**两者都比 Go 宽，且没有任何编译期或运行期提示。**

实测（两侧各枚举全部 0x110000 码点后做集合差，脚本在 `/tmp/rgoc-m1-demo/`）：

| 谓词 | Go（oracle, Unicode 17.0.0） | Rust std | 差 |
|---|---|---|---|
| 字母 | `unicode.IsLetter` **145,672** 码点 / 684 区间 | `is_alphabetic` 147,421 | **Rust 多 1,749**（全为 Mn，如 U+0345） |
| 数字 | `unicode.IsDigit`(Nd) **770** 码点 / 72 区间 | `is_numeric` 1,924 | **Rust 多 1,154**（全为 No，如 U+00B2 `²`） |

⇒ 合计 **2,903 个码点**行为不同。后果：`x²` 在 Go 里是 `x` + 非法字符，
用 Rust std 会**整个切成一个标识符** —— 静默错误。
⇒ 反向为 0（Go 认为是字母的，Rust 一个不漏）⇒ 差异是**单向放宽**。

**✅ 解法（不引第三方依赖）**：用 **oracle 自己生成**两张区间表 ——
`unicode.IsLetter` → 684 区间、`unicode.IsDigit` → 72 区间，共 **756 区间 ≈ 5.9 KB 数据**
（`&[(u32,u32)]`），落成 `rgoc-lex/src/unicode_tables.rs`，文件头注明「由 go1.27.1 的 unicode 包
导出、Unicode 17.0.0、勿手改」。好处：**表由 oracle 生成 ⇒ 天然与 oracle 一致**，
且绕开 `03` §2「不默认引入新第三方依赖（新增须单独授权）」。
⚠️ 注意 `unicode-ident` crate（Cargo.lock 里已有，是 syn 的传递依赖）**也不适用** ——
它实现 UAX#31 的 XID，与 Go 的「广义类别」规则不同。

**规模数据（备查）**：语料 11,480 个 `.go`，共 94.2 MB，**最大 3.77 MB**（`ssa/opGen.go`），均值 8.4 KB
⇒ 单文件上限 **64 MiB = 最大文件的 17 倍**，有据可依。
待 vendor 的 5 个官方文件共 **1,374 行**（scanner 881 / source 218 / tokens 159 /
token_string 70 / operator_string 46）。

- **R5** 设计 §7.2 的诊断表**凭印象手写**，漏 4 条且**不报错** ⇒ 改为**枚举**全部报错点
  （26 处 ⇒ 25 条消息模板），`DiagCode` 19 → **23**。
- **R6** **`RGOC_TTY=0`**：`in-container.sh` 在 stdin 是 tty 时加 `-it`，伪终端 ONLCR 把
  `\n` 翻成 `\r\n` —— **终端里看不出来**。实测 20 行含 20 个 CR vs 0 个。已加为计划 **G12**。
- **R7** `String` **装不下实测行为**：`78 FF 20 79` ⇒ `name lit="x\xff"` —— 标识符原文里有非法 UTF-8。
  ⇒ 载荷改 **`Vec<u8>`**（新增 D-M1-12）。**范围刻意收窄**：NUL/BOM/私有区都是合法 UTF-8，能进 `String`。

### 新坐实的实测事实（design §2.3 F21–F25）

- **F21** 官方对 `=` / `:=` / `<-` **不设 `op`**（`scanner.go:42` 的有效域不含这三者）
- **F22** 标识符原文**可含非法 UTF-8**
- **F23** **`bad=false` 与「原文含非法字节」可同时成立**（`1\xff2` 是 `kind=0 bad=false`）
  ⇒ **`bad` 只反映字面量语法，不等于"原文可信"**
- **F24** 官方诊断消息模板去重后 **25** 条（26 处错误调用点）
- **F25** 伪终端 ONLCR（见 R6）

### 方法论收获（本轮最重要的两条）

1. **跨语言对撞断言**：`test_diag.rs` 用 `CARGO_MANIFEST_DIR` 读 `tools/token-oracle/diagmap.go`，
