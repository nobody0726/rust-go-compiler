## Task 7（实例化后的可赋值）—— 三个「判据无牙」的坑
* **`var _ int = …` 无牙**：`_` 是空标识符，`assignment(target=None)` 直接放行；
  `var` 声明面从 M4 起也不判可赋值性。探针已证替换正确（`results after subst =
  ["string"]`）而负例仍绿 ⇒ 一律写 `var x int` + `x = …`。
* **负例形参若写 `[]T` 也无牙**：旧路径自己就报（`[]string` vs `[]T` 判假）⇒
  注入「不替换」变异时它照样绿。改用**裸 `T`**（`Id[T any](v T) T`）才只在返回类型面有牙。
* **变参泛型调用会 panic（rc=101）**：`infer_for_call` 有「形参表与实参表必须等长」的
  `assert!`，官方是先按 `call.go` 的 `arguments` 打包末尾实参再推断。踩点
  `test/typeparam/slices.go`。修法 = **这一档不推断**（`sig.variadic || 长度不等 ⇒ 原样`），
  不是放宽断言。
* clippy `type_complexity` ⇒ 建具名结构体 `InstSig`，不用 `#[allow]`。

## Task 9（类型参数上的内建）—— 最大产出是「类型参数进作用域」
* `stmt::declare_tparams`：泛型函数体里 `type_expr(T)` **一直失败**，因为
  `pkg.lookup_in_file` 只有「文件 → 包 → universe」三层，看不见函数级类型参数。
  而 `make` 的写法是 `let Some(t) = cx.type_expr(…) else { return invalid }`
  ⇒ **`make` 面在泛型函数体里等于没检查**（`builtins.go` 的 `make(S1, 10)` 零诊断）。
  修法：`func_decl` push 函数层后把 `[T any]` 的名字声明进 `Env`
  （`Operand::type_expr(self_ty)`），名字与 `pkg.generic_funcs` 的 id 按声明序配对。
* 四个 helper（官方也是四个）：`under_is`（每 term 底层满足）/ `common_under`
  （共同底层）/ `common_slice_elem`（`append` 要同一个 `[]E`）/ `common_map_key`
  （`delete` 的 key 一致）。
* ⚠️ **回归教训**：`declare_tparams` 让 3 个文件（`issue48537/48538/issue50833`）
  从过变不过，全是 `CHK-INVALID-LIT` —— 以前 `type_expr(T)` 失败 ⇒ 复合字面量面
  **静默跳过**；现在解析成功 ⇒ 走进分类 ⇒ 落 `Shape::Other`。
  修法：复合字面量三处（hint 剥指针 / 形状分类 / 字段查找基类型）都按 `common_under` 归一。
  **让一个「以前静默」的面开始工作，会把它的所有缺口一次性暴露。**
* 读数：门禁族 check **93 → 96/111**（run 58→61，零回归）；
  `CHK-INVALID-INDEX` 3→0、`CHK-INVALID-LIT` 3→0、`CHK-INVALID-ASSIGN` 8→5、
  `CHK-INVALID-BUILTIN-ARG` 2→1；`t_gen_08a` 73→76；全量 2292/1/2；三态全绿。
* open：`builtins.go` 的 `g3[T M4[rune, V]]` —— 探针实测 term 底层是

## M12/Task 10（两个边角：`_` 与 `range`）—— 一句话：「声明位置」不是「引用位置」

* **① 接收者的形参表不解析**。官方 `collectRecv`（`signature.go:216`）= `unpackRecv`
  拆出「指针 + 基 + 形参表」→ 形参逐个 `declareTypeParam`（`decl.go:662`）→
  `instance(baseType, recvTParams)`。**实参是刚声明的类型参数自己**，形参那棵表达式
  从不过 `typ()`。所以 `func (b Box[_]) M()` 的 `_` 是**声明**。
  本仓原来两半都做了却没接上：`recv_tparam_fields` 已按官方收了声明，
  但 `resolve_func_sig` 又把整棵 `Box[_]` 交给 `resolve_type` ⇒ `Expr::Index`
  分支把 `[_]` 当类型实参解析 ⇒ `TYP-INVALID-BLANK`（4 个文件）。
  修法：`resolve_recv_generic` —— 剥 `Paren`/`*` 记层数、只解析基名、按层数
  `add_pointer` 包回。**不做 `_` 特判**：`Box[Undef]` 同一个洞。
* ⚠️ **接收者改法必须用 dump 验，不能只看测试绿**：`recv_named` 只剥一层指针再看基底
  ⇒ **指针丢了它也返回 `Some`** ⇒ 挂方法对指针丢失免疫，测试不会红。
  实测三个方法 recv = `pointer #0` / `#0` / `pointer #0`，一个没丢。
* **② `range` 第一句是 `commonUnder`**（`range.go:212`）不是 `under`。
  `under(TypeParam)` 官方返回**它自己** ⇒ `switch` 落 default ⇒
  `~map[K]V` 上的 `range` 被误报。改用 `common_under`（Task 9 的）：
  「无共同底层 ⇒ None」正好是官方那条；非类型参数仍走 `underlying`（逐字等价，
  `for i := range MyInt(10)` 的 key 仍是 `MyInt`）。
* 三个变异全红：①换回全量解析 ⇒ `gen10a` 红；②换回 `underlying` ⇒ `gen10c`
  四形态全红；③`common_under` 的 term 循环 `.take(1)` ⇒ `gen09n2` + `gen10n3`
  同时红（两个负例钉在同一处「共同」语义）。
* 读数：门禁族 check **96 → 101/116**（run 61→62、compile 33→**37**，零回归）；
  `TYP-INVALID-BLANK` 与 `CHK-INVALID-RANGE-EXPR` 两个码在门禁面下清零；
