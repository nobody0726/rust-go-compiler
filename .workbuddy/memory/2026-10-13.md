## ▶️ 环境变更 1：DSH Web GUI 会话恢复（cookie 注入 Chrome）

**现象**：`http://127.0.0.1:19387` 显示
`dsh web authentication required; reopen the URL printed by dsh web.`

**根因**（本次排查的结论，值得记）：
- 那行带 token 的 URL 只在 **CLI**（`dsh web`）启动时 `console.log`；
- 本机是**桌面 App**（`dsh-desktop-host`，pid 77798），带 token 的 URL 只经 `process.send`
  IPC 交给 Electron 去开浏览器，**不打印、不写日志**；浏览器那次自动打开没成功 → 没换取 cookie → 401。
- token 是**进程内一次性随机值**（`processLaunchToken`，32B base64url），因此：
  统一日志里没有（`log show` 只有 XCTest 噪声）、`ps`/环境变量里没有
  （`DSH_WEB_URL` **故意**只给干净 URL）、lldb attach 被拒
  （`Not allowed to attach to process`）→ **不可事后恢复**。

**解法**：绕开 token，直接复现它换取的**会话 cookie**。
- 方案（app bundle 内 `@deepseek-ai/dsh-client-connection` 实测读出）：
  cookie 名 = `dsh-auth-` + base64url(sha256(authority))；
  值 = `v1.` + base64url(JSON{version:1,authority,issuedAt,expiresAt}) + `.` + base64url(HMAC-SHA256(secret,body))；
  authority = `127.0.0.1:19387`（**绑定 Host，含端口**）；secret 取
  `~/.dsh/.credentials.yaml` 的 `client-connection/browser-session`。
- 自检：带 cookie 请求 `/` → **200**；不带 → **401**。
- 注入浏览器：**Chrome 154（macOS）认「明文行」**——`cookies` 表 `value` 填值、
  `encrypted_value` 留空（`x''`），Chrome 照读。这条是**一次性 profile 实测**得出的
  （`document.cookie` 真读到插入的明文 cookie），不是在真 profile 上试错。
  ⚠️ 不要再去逆向 macOS 的 v10 AES-128-CBC+GCM 那套（PBKDF2-HMAC-SHA1/saltysalt/1003 能解出
  真 cookie，但明文前 16B 是 Chrome 的域摘要，构造容易出错）。

**回滚点**：`~/Library/Application Support/Google/Chrome/Default/Cookies.bak-20261012143109`。
**有效期**：cookie 到 2026-11-11；重生成脚本 `/tmp/dsh-auth-into-chrome.mjs`（未入库，会随 /tmp 清理）。

**留了一条待办**：桌面版缺少等价于 `dsh web:` 的 URL 入口 —— 浏览器自动打开一旦失败，
用户没有任何可复制的登录入口。这属于 **DSH 上游缺口**，不是本仓问题。

## ▶️ 环境变更 2：全局安装 superpowers 插件（`desktop` profile）

**用户要求**：「全局安装下 superpower 插件」。

**选型**（npm 上同名近似的有两个，选了前者）：
| 包 | 版本 | 维护者 | 上月下载 | 备注 |
|---|---|---|---|---|
| **`superpowers-dsh`** ✅ | 0.2.0 | LayneChai | **2720** | 技能同步自 obra/superpowers **v6.4.2**，15 个技能 |
| `dsh-plugin-superpowers` | 0.1.2 | LittleBlackTong | 419 | 同为 obra 移植，14 个技能 |

**安装**（DSH 的「全局」= 装进 profile，不是 npm -g）：
```sh
/Applications/DeepSeek\ Harness.app/Contents/Resources/runtime/cli/bin/dsh \
  plugin --profile desktop add superpowers-dsh
```
结果：`pnpm v11.7.0` 7.7 s 成功 → `~/.dsh/profiles/desktop/package.json` 里
`dependencies` 加 `superpowers-dsh: ^0.2.0`，`dsh.profile.bundles` **追加 `superpowers-dsh`**
（顺序：`dsh-base` → `dsh-web-app` → `dsh-experimental-schedule-bundle` → `superpowers-dsh`）。

**它是怎么生效的**（读包内 `cordis.patch.yml` + `lib/index.js` 得到，不是猜的）：
```yaml
- insert:
    - id: superpowers-dsh
      name: 'superpowers-dsh'
```
该插件向 **`ctx.skills` 注册表的 host 层**注册一个 skill provider
（`inject = ['skills']`，`PACKAGED_SKILL_RANK = 550`，排在本地内建根之下），
技能正文按 `import.meta.url` 定位 `skills/<name>/SKILL.md`，**按需加载**。
包**零 dependencies / 零 peerDependencies**，所以不需要任何版本豁免或额外安装。

**验证证据**：
- ✅ **本会话的技能目录当场多出 15 条**（`brainstorming` / `systematic-debugging` /
  `test-driven-development` / `subagent-driven-development` / `writing-plans` /
  `using-superpowers` …）——**无需重启即已生效**，这是最直接的端到端证据；
- ✅ 15 个 `SKILL.md` 全部有 `name:` + `description:` frontmatter（0 问题）；
- ✅ profile manifest 的 `bundles` 与 `dependencies` 均已落盘。

**注意**：`dsh --profile desktop --dump-config` **不能用来验证** ——
会报 `error: profile "desktop" is managed exclusively by the Electron application`。
这本身也是一条环境事实：桌面 profile 的配置只能靠「技能目录是否出现」来验。

**回滚**：删 `~/.dsh/profiles/desktop/package.json` 里的 `superpowers-dsh` 两处引用后
`dsh plugin --profile desktop remove superpowers-dsh`；旧 package.json 备份在
`/tmp/desktop-package.json.bak-*`（未入库）。
