## M2 前置调研：官方 parser 的递归下降结构（读代码所得，非猜测）

- `parser.go:17` 是 **`const trace = false`** —— 官方 parser **自带缩进式递归轨迹打印**
  （`p.trace(msg) func()` + `p.print` 用 `p.line` 和 `p.indent`），只是编译期关掉。
  **语料只读 ⇒ 不能为了看轨迹改 const**。替代做法：按官方同一套结构写「教学用镜像实现」
  （本次产出 `/tmp/rd_demo.py`，**临时文件，未入仓**）来打印轨迹。
- 官方把 **EBNF 规则直接写成函数上方的注释**（`// Expression = UnaryExpr | Expression binary_op Expression .`）。
  ⇒ M2-design 可以直接以「规则 ↔ 函数」对照表为骨架，不需要自己重新发明。
- 三种递归形状与手法（已确认，可直接写进 M2-design）：
  1. 左递归 → **优先级爬升**：`binaryExpr(x, prec)` + `for ... p.prec > prec`。
     **`>` 是左结合的全部秘密**；写成 `>=` 就变右结合。
     `expr()` 只是 `binaryExpr(nil, 0)` 的壳。
     ⚠️ 官方**故意不给 binaryExpr 加 trace**（注释：`don't trace binaryExpr - only leads
     to overly nested trace output`）。
  2. 右递归 → 直接递归调用（`unaryExpr` 里 `x.X = p.unaryExpr()`）。
  3. 后缀/列表左递归 → `for + switch p.tok`（`pexpr` 的 `loop: for {...}`）。
- **非 LL(1) 的地方只有几处**，都是靠显式上下文状态，不是靠多遍扫描：
  - `p.xnest`：**complit 二义消解**（`T{...}` 是类型转换还是字面量）；`header()` 里
    `p.xnest = -1` 显式**禁用**（if/for 头部的 `{` 必是块）。
  - `header()` 的**分号哨兵**：先 `simpleStmt` 解析头部，再按「有没有吃到 `;`」决定
    这段是 init 还是 cond；最后 **unpack condStmt**（`*ExprStmt` → `s.X`）。
    ⚠️ 顺带解释了经典的 `=` 写成 `==` 诊断为什么在这里报：`p.header` 的 unpack 里专门为
    `*AssignStmt && Op == 0` 定制了消息（源码注释点名 go.dev/issue 相关）。
  - `arrayOrTArgs()`：`x[n]E`（数组类型）vs `x[n]`/`x[n,]`（IndexExpr）靠
    `typeList(false)` 返回的 **comma 标志** + `typeOrNil()` 前瞻消解。
  - `advance(followlist...)`：错误恢复 **FOLLOW 集跳读**；`stopset`（break/const/...
    16 个语句起始关键字）**只在函数体内（`p.fnest > 0`）才纳入**；followlist 为空时
    **恰好消费一个非 EOF 词元以保证推进**。
- `Mode` 只有一个位：`CheckBranches`（标签跳转目标回填，实现见 `branches.go`）。
- 推论（M2 的三条风险）：① 递归深度 = 输入嵌套深度 ⇒ 需要上限（与 M1 的 64 MiB 上限同族）；
  ② 上下文标志（xnest 等）必须**显式建模**，否则会退化成隐式两遍解析；
  ③ `dumper.go` 的 `Fdump` 自述「no specific output format is guaranteed」⇒ 不能当 golden。

## M2 前置调研：位置保真与二义消解（本轮问答产出，M2-design 直接可用）

### 位置保真：官方是三机制，不是「记得越全越好」

1. **产生**：每个节点在「看到某个词元的那一刻」取 `p.pos()`（= `MakePos(p.base, line, col)`），
   **绝不从子节点聚合**。⇒ **每个节点记的是哪个词元，逐节点不同**，必须做成显式表：
   `BinaryExpr/UnaryExpr/AssignStmt` → 运算符；`SelectorExpr/AssertExpr/TypeSwitchGuard` → `.`；
   `CallExpr` → `(`；`IndexExpr/SliceExpr` → `[`；`IfStmt` → `if`；`File` → `package`；
   `FuncDecl` → `func`。**验证手段 = `nodes_test.go:TestPos`**：157 个 snippet，用 `@`
   标出期望列号，strip 后解析，**同时断言 `typeOf(node)` 与 `node.Pos().Col() == index+colbase`**。
   这个格式 M2 可直接照抄（oracle-free 的自证判据，比 AST dump 稳）。
2. **双视图**：官方 `Pos = {base *PosBase, line, col uint32}` —— 节点只存**真实** line/col，
   `//line` 只换 **base**。`pos.go:115 String()` 同时输出两个读数：
   `fake.go:45:1[main.go:7:1]`（相对[绝对]）。`RelLine() = b.Line() + (pos.Line() - b.Pos().Line())`。
   ⚠️ **这对 C1 是硬影响**：C1 的 `Pos{file,line,col}` **没有 base**，照官方做必须**扩展 C1**
   （C1 §6 已把「多源位置映射」登记为 M2/M4 需求，正好在此落地）。
   若选择就地改写 line/col，就会丢掉真实位置 ⇒ 「位置可追溯到字节」这条契约作废。
3. **改写**：`updateBase()`（parser.go:124）解析 `//line f:l[:c]` 三种形态（空文件名继承上一个），
   产出 `NewLineBase(pos, filename, trimmed, line, col)`；`//line` 必须是行首（`col == colbase`）
   或块注释，行注释的生效位置是**下一行**。
   **实测证据**（本轮在容器内用 go1.27.1 跑）：源码 `main.go` 真实第 7 行的 `}`，
   报错为 `./fake.go:45: syntax error`（42 + (7-4) = 45，算术完全吻合）。
   另外 `p.init` 里顺带解析 `//go:build` → `p.goVersion = constraint.GoVersion(x)`
   （即 `File.GoVersion` 的**唯一**来源，M2 必须实现这条，不能只存文本）。

### 二义消解：四种手段，**没有一种是回溯**

| 手段 | 真实例子 | 机制 |
|---|---|---|
| 上下文标志 | complit：`pexpr` 的 `case _Lbrace`（parser.go:1218） | `Unparen(x)` + 形状 switch + `p.xnest >= 0` + `isValue(t)`；不成立就 **`break loop` 把 `{` 留给上层** |
| 上下文标志 | 括号：`operand(keep_parens)`（1030-1050） | `T{}` 里 `T` 不许带括号（`p.tok == _Lbrace` 时强制 keep）；`go/defer` 必须保留 |
| 先解析后拆包 | if/for 头（`header` 2352 + unpack 2420） | 分号哨兵；`*ExprStmt` → `s.X`；`=` 写成 `==` 的经典诊断就在 unpack 的 default 分支 |
| 解析到能区分 | `arrayOrTArgs`（1711） | `typeList(false)` 的 **comma 标志** + `typeOrNil()` 前瞻 |
| 兜底（错误恢复） | `advance(followlist)`（345） | FOLLOW 集跳读；`stopset`（16 个语句起始关键字）**只在 `p.fnest > 0` 才纳入**；followlist 为空时**恰好吃一个非 EOF 词元保证推进** |

### 解析过程的形状（M2 的模块划分依据）

四层分派 + 三条状态 + 两个旁路：
- 四层：词元层 `p.next()`（分号插入已在 M1 完成，这里只管 pragma/错误）→ 声明层
  `fileOrNil()`/`list()`（逗号/分号列表的通用机制 + "possibly missing" 诊断）→ 语句层
  `stmtOrNil()`（**先查 `_Name`**，官方注释：多数语句以标识符开头，先便宜地分流）→
  表达式层 `expr→binaryExpr→unaryExpr→pexpr→operand` → 收尾 `CheckBranches`（可选 mode）。
- 三条状态：`p.tok`（唯一前瞻）/ `p.fnest`（是否函数体内，决定 stopset）/ `p.xnest`（表达式嵌套，complit 总开关，`-1`=禁用）。
- 两个旁路：诊断（`errorAt`→DiagBag）与 pragma（`pragh` 回调，`p.scanner.blank` 提供「前面是否空行」）。

## 从第一性原理梳理 M2 的输入/输出/处理（未改任何代码/文档）

用户问 M2 的输入/输出/处理是什么，要求从第一性原理出发。结论记录如下（为后续 M2-design 开工做认知准备）：

- **根本矛盾**：Go 源码语义结构是嵌套的（树），M1 给的是线性的（词元流）。M2 的唯一存在意义 = 把线性重建为树。
- **输入**（来自 M1）：① 词元流（类别+载荷+Pos，只有先后无归属）② 注释/指令文本（//line //go: 原文，M1 只识别不解析）③ Pos/FileTable（C1 已完整）。
- **处理**（parser 5 件事）：① 分组（语法规则定归属）② 建树（组装 AST 节点）③ 位置保真（节点记 Pos，C1 延续）④ 错误恢复（报错继续，BadExpr 占位）⑤ //line 重映射（updateBase，M1 F11 推迟）+ //go: 解析（只认不生效，M7+）。
- **输出**（交 M3/M4）：① AST（树，AST-01..49，节点=语法构造 边=包含）② 诊断流（语法错误，沿用 C1 DiagCode）③ 重映射后位置 + 指令记号。
- **边界**（不做）：类型(M3) / 常量值(M3) / 作用域(M3) / 包import语义(M3) / //go:效果(M7+) / 代码生成(M6/M7)。roadmap M2 门禁原文："parser 测试不等于 run/compile 全集已支持"。
- **M2-design 开工时会撞到的 4 个分叉**（当时要逐个拍板）：① AST 节点扁平结构体 vs Rust 和类型 enum ② 手写递归下降 vs 生成器（官方手写）③ 错误恢复深度（roadmap 砍项"砍广泛恢复策略"）④ //go: 已知指令清单（"先支持解析与拒绝未知关键指令"）。

### T-AP10 的三条新硬事实（下次直接用）

1. **`prec` 是词法层知识，绝不能抄进 parser 的 followset**。`Follow::Plain(Operator)` 只比
   `(form, op)` 两枚词法字段。抄一份优先级表的后果是「抄错的那份永远不命中」，而症状是
   「恢复点提前停住 ⇒ 少收/多收一段」—— **不报错**，到 oracle 对撞才暴露。
2. **节点位置只能取 `Expr::pos()`，不能取 `self.tok.pos`**。`a.b` 的节点位置是 `a`；解析到逗号时
   `tok.pos` 指向 `,` ⇒ 后半段一错位置整段漂。**反向验证 M4**（把 `Operation.pos` 改成左操作数位置）
   让位置断言精确变红，证明这些断言真在比具体值。
3. **`Op::Tilde` 是回源逐项 diff 官方 `Operator` 才发现的漏项**（T-AP01 定义的 `Op` 少了它）。
   症状与 `PA-1` 的同形：**"能编译 + 断言全绿"对数据模型不构成正确性证据**（断言全是构造字面量）。
   已在 `aux.rs` 补一张**变体集对齐表**（`Recv`→`Arrow`、`Div`→`Quo` 的改名对照）。
