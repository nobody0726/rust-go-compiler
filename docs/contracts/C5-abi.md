## 1. 目标平台（首发固定）

| 项 | 值 | 来源 |
|---|---|---|
| 目标三元组 | `aarch64-unknown-linux-gnu` | `03` §0.2 |
| 架构 | ARM aarch64（64 位 little-endian） | 实测 `file` 判定 |
| 寄存器宽度 | 64 位（`x0`–`x30`） | AAPCS64 |
| 产物 | ELF 64-bit LSB PIE | 实测 `file` 输出 |

**已验证**（`T-S3-02`）：产物 `file` 判定**同时**含 `ELF 64-bit LSB` **与** `ARM aarch64`。

> **为什么必须判两个条件**：x86-64 的 ELF 同样含 `ELF 64-bit LSB`。
> 只判那一个会漏掉「链接到了错误架构」—— 而那在跨平台机器上很容易发生。
> 有测试 `t_s3_02_*` 钉住**两个**条件都要断言。

## 2. 六项记录（`T-S3-04` 的逐条固化）

### 2.1 调用约定

**结论**：裸 `_start`，**不经 C 运行时**。系统调用参数走 `x0..x5`，
返回值在 `x0`，**系统调用号在 `x8`**，用 `svc #0` 陷入内核。

| 调用 | 号 | 参数 | 返回 |
|---|---|---|---|
| `write` | **64** | `x0`=fd，`x1`=buf，`x2`=count | `x0`=实际写入字节数 |
| `exit_group` | **94** | `x0`=状态码 | 不返回 |

**必须用 `exit_group`（94）而非 `exit`（60）**：多线程下 `exit` 只退出当前线程。

**未验证**（缺口）：只验证了「**无参、无返回**」的系统调用。
一旦有用户函数，以下**全部未验证**：参数传递、被调用方栈帧、
callee-saved 寄存器（`x19`–`x28`）的保存义务。**那是 M7 的内容。**
→ **答案见 §6。**

### 2.2 栈对齐

**结论**：本 fixture **完全不动栈** —— 没有 `push`、没有 `bl`、没有局部变量，
所以 `sp` 始终是进程入口时的值，**天然满足 16 字节对齐**。

**⚠️ 「不需要动栈」不等于「栈对齐已验证」**（有测试专门钉这句：`t_s3_04_栈对齐项不得声称已验证`）：

| 未验证 | 说明 |
|---|---|
| `bl` 前的 16 字节对齐 | AAPCS64 要求每次函数调用前 `sp` 保持 16 字节对齐 |
| leaf 函数不保存 `fp`/`lr` | 叶子函数可不保存链接寄存器 |
| 非 leaf 必须保存 | 非叶子函数**必须**保存 `fp`(x29) 与 `lr`(x30) |
| 栈帧大小向上取整 | 局部变量布局后 `sp` 仍须 16 字节对齐 |

**归属**：M7。 → **答案见 §7。**

### 2.3 输出流

**结论**：走 `write(2)` 系统调用，`x0` = fd（**1 = stdout**、**2 = stderr**）。

**已验证**：
- `x1` 用 **`adrp` + `add :lo12:`** 取数据段地址 —— **PIE 下不能用绝对地址**（有测试钉住不得出现 `ldr x1, =`）
- fixture 声明 `Stream::Stdout` ⇒ 用 fd 1；`Stream::Stderr` ⇒ 用 fd 2（有测试钉住两者**不同**）

**⚠️ 已知缺口（代码里留了 `TODO(S3-04)` 标记）**：
**未处理 `write` 的部分写（短写）返回值。**
Linux 上 `write` 可能只写一部分，真实实现**必须循环**。
fixture 只有 6 字节，实践中不触发 —— 所以不能假装处理了。

**归属**：M7。 → **短写由 `rt_write` 的循环处理，见 `M7-design.md` §3.6。**

### 2.4 退出码

**结论**：`exit_group(2)`，`x0` = 状态码；正常结束写 **0**。

**已验证**：运行该 ELF 的退出码为 `0`（`T-S3-03`）。

**未验证**：非零退出码的路径；**Go 的 panic 退出码是 2**（与本条不同），
「什么情况下 rgoc 该用哪个」尚未决定 → **M5e**（panic/recover）。
→ **答案见 `C9` §5：正常 0 / 静态诊断 1 / panic 与资源超限 2。**

### 2.5 最小 runtime 桥接

**结论**：**零 libc 符号** —— `svc #0` 直达内核，不需要任何库函数。
但链接产物**仍然是动态链接**（`readelf -d` 显示 `NEEDED libc.so.6`），
那是**链接器默认加的，我们一个符号都没引用**。

| 开关 | 状态 | 不加会怎样（实测） |
|---|---|---|
| `-nostartfiles` | **必需** | **链接失败**：`multiple definition of _start; /lib/aarch64-linux-gnu/Scrt1.o: first defined here` + `undefined reference to main` |
| `-Wl,-s` | **必需** | 链接成功但**产物不可复现**（见 §3） |
| `-static` | **故意不加** | 能链，但变成 static-pie 且体积更大；会掩盖「到底依赖了什么」 |

> `-nostartfiles` 的原因：C 运行时启动文件 `Scrt1.o` **已经定义了 `_start`**，
> 与我们手写的 `_start` 冲突。裸汇编程序必须显式去掉它。

**「不引用 libc 符号」不等于「不需要 libc」**（有测试专门钉这句）。
要真正静态还得加 `-static`，M0 故意不加。

**⚠️ `-Wl,-s` 的代价**：产物**没有符号表** ⇒ 对运行无影响，但**不可符号级调试**
（无函数名、无行号）。将来若要对生成物做符号级调试，
必须去掉 `-s` 并改用「按 section 比对」而非「整文件逐字节比对」。

**rgoc 真正的 runtime**（map / scheduler / GC）**完全未涉及** ——
`03` §M5 明确「宿主管理内存但仍监控运行预算」，那是 M5 起的事。

### 2.6 unwind 边界

**结论**：**不可 unwind**。生成的汇编**没有 `.cfi_*` 指令**，
链接产物也**没有 `.eh_frame` 段**。任何栈回溯（panic 打印调用栈、`backtrace(3)`）
都拿不到信息。

**这是当前形态的固有限制，不是待办**。要支持 unwind 就得在每条指令后维护
CFI 行号表并保证与 unwind 表同步 —— 那是**独立的一块工作**。

**写下来的理由**：将来有人加 `-fasynchronous-unwind-tables` 时，
要知道这是**新增能力**而非「本来就支持」。

**与 M5 的对齐问题**（待解决）：M5 的 panic 沿栈向上传播
与 M7 的 unwind 能力**是同一套机制还是两套**？M0 无法回答 ——
因为 M0 连 unwind 都没有。
→ **M7 的回答：native 侧没有 unwind。panic 是「打印一行 + `exit_group(2)`」，
不沿栈传播（`M7-design.md` §3.9）。**

## 3. 产物可复现性（`T-S3-05` 的实测结论）

**不加 `-Wl,-s` 时，同一份汇编重复链接三次，产物字节不一致**：

```text
$ for i in 1 2 3; do clang -nostartfiles -o out$i.elf hello.s; done
$ cmp out1.elf out2.elf
out1.elf out2.elf differ: char 66200, line 4
```

**定位链（三步，每步都必要）**：

1. **BuildID 三次完全相同**（`84a05590…`）—— BuildID 是**内容哈希**，
   相同即证明**代码内容本身可复现**；
2. **文件大小三次相同**（67384 字节）—— 排除「长度不同」这一类；
3. `readelf -p .strtab` 打出根因：

   ```text
   String dump of section '.strtab':
     [     1]  hello-d9450b.o     ← ★ 随机后缀
   ```

   那是 **clang 汇编器生成的中间目标文件名**，以 `STT_FILE` 符号留在符号表。

**处置**：加 `-Wl,-s` 后三次**逐字节相同**（66480 字节）且程序照常运行。

> **这不是为了让测试通过而放宽判定** ——
> 符号表对可执行文件的**运行**毫无作用；剥掉它反而让「结果一致」这条门禁
> **真正约束到 rgoc 自己的产物**上。

**对下游的约束**：M7 若要保留符号表（为了可调试），
则产物比对**必须改成按 section 比对**，不能整文件逐字节。
→ M7 的选择：**保留 `-Wl,-s`**，比对仍是整文件逐字节（`T-NAT-49` 带反向守卫）。

## 4. 对象布局 / 栈帧布局：**M0 完全未涉及**

| 主题 | M0 状态 | 归属 |
|---|---|---|
| **栈帧布局**（局部变量的偏移、对齐、溢出区） | ❌ 零局部变量 ⇒ **无布局可言** | M7 → **§7** |
| **对象布局**（struct 字段偏移/对齐/填充、interface 值、slice 描述符、map） | ❌ 完全未涉及 | M5（值语义）/ M7（物理布局，**只做字段偏移的消费方**）→ **§7.3** |
| **参数传递**（超过 `x0`–`x7` 怎么办、栈上传参） | ❌ 只有 `write` 的 3 个参数 | M7 → **§6** |
| **返回值**（多于一个返回值时怎么返回） | ❌ 未涉及 | M5b / M7 → **§6** |
| **对齐规则**（各类型的对齐要求） | ❌ 未涉及 | M5 → M7 只**消费** `rgoc-types` 的布局，不自算 |

**为什么 M0 不猜这些**：布局规则的**每一个数字**都会在 M7 被大量引用，
而 M0 没有任何实测依据 —— 写下来的只会是「看起来合理」的猜测，
而**猜测被当成结论**正是 `03` §M4 的 M3「砍项」反复警告的事。

## 5. runtime symbol bridge：**M0 只验证了「不需要」**

M0 的结论是**否定的**，但这个否定本身有价值：

| 问题 | M0 的回答 |
|---|---|
| 最小可运行程序需要 runtime 吗？ | **不需要** —— `svc #0` 直达内核 |
| 需要 libc 吗？ | **不引用任何 libc 符号**（但产物仍动态链接） |
| 需要 scheduler 吗？ | **不需要**（单线程直线执行） |
| 需要 GC / 分配器吗？ | **不需要**（无堆分配，`hello` 在 `.data` 段） |

**它证明的是「后端路线可行」，不是「rgoc 的 runtime 已设计」**。
`03` §M5 明确：宿主管理内存但监控预算；M9 才有 Go 语义完整的 map/GC。

→ **M7 的 runtime 是 freestanding C 的一个 `.o`（`rt.c`），不是 libc**（`M7-design.md` `D-M7-4`）。

## 6. 调用约定（M7 新增，**冻结**）

### 6.1 rgoc-AAPCS64 子集

| 项 | 约定 |
|---|---|
| 整数 / 指针 / `bool` 实参 | `x0..x7` |
| 超出 8 个的实参 | 调用方帧尾的 outgoing 区，`[sp, #k*8]`（16 对齐） |
| 浮点实参 | `v0..v7`（**独立计数**，与 `x` 不共用序号） |
| `complex64` 实参 | **1 个 `v`**（两个 `f32` 打包在一个 64 位寄存器里） |
| `complex128` 实参 | **2 个 `v`**（`re` 低、`im` 高） |
| 聚合实参（数组 / struct） | **一律按指针**：调用方在**自己的帧**里放副本，传地址 |
| 整数返回值 | `x0..x7` |
| 浮点返回值 | `v0..v7` |
| 多返回值 | 按结果顺序**依次**占用 `x` / `v` 两个序列 |
| 聚合返回值 | 调用方在**自己的帧**里留缓冲，地址进 `x8` |
| 被调方保存 | `x19..x29` / `v8..v15` —— **生成代码一律不用** |
| `sp` | **恒 16 字节对齐**（进入函数时 / 每次 `bl` 前 / 每次 `svc` 前） |
| 栈方向 | 向下增长；序言 `sub sp, sp, #frame`，尾声 `add sp, sp, #frame` |

### 6.2 与 AAPCS64 的三处**故意不同**

| # | 差异 | 为什么 |
|---|---|---|
| 1 | 聚合**按指针**传，不跟「≤16 字节按值」的规则 | `print` 的实参面不含复合值（`C9` §4.3），按值传的分支我们**没有用例去验**；没验过的分支等于没有 |
| 2 | 生成代码**不用** callee-saved 寄存器 | 值全在栈槽（`D-M7-3`），寄存器活不过一条指令 ⇒ 序言里没有 save/restore，帧里只有 `fp`/`lr` 两项 |
| 3 | 不实现 HFA / HVA 规则 | 同上：没有用例。`complex` 走「2 个 `v`」是**我们自己**的约定，不是 HFA |

> **runtime 的 C 函数**：它按标准 AAPCS64 编译（clang 会自己保存 `x19..x28`）。
> 我们的生成代码不碰这些寄存器，所以两边不冲突 —— 「不用」比「保存」更强。

### 6.3 为什么可以自定

roadmap §M7 明确「**不用 Go internal ABI 作门槛**」，而 M7 的所有调用方与被调方
**都是我们生成的代码**（M6 已拒函数值与接口动态派发）。唯一的「外部」是被 `rt.c`
导出的 runtime 函数 —— 它们在 §6.1 的标量部分与 AAPCS64 完全一致，所以能直接调。

## 7. 帧布局（M7 新增，**槽宽与对齐冻结**）

### 7.1 形状

```text
高地址
  ┌──────────────────────────┐
  │ 调用方的 outgoing 实参区   │  ← 由调用方在自己的帧尾预留（16 对齐）
  ├──────────────────────────┤ ← fp (x29)
  │ saved fp                 │  +0
  │ saved lr                 │  +8
  ├──────────────────────────┤
  │ 值槽区（按 ValueId 升序）  │  第一个槽 off = -24（占 [fp-24, fp-16)）
  ├──────────────────────────┤
  │ 取址槽区（slot_types）     │  进帧时按类型清零
  ├──────────────────────────┤
  │ 并行拷贝临时区             │  最大 = 单边实参个数 × 8
  └──────────────────────────┘ ← sp
低地址
```

### 7.2 槽宽与对齐（冻结）

| 类型 | 槽宽（字节） | 对齐 |
|---|---|---|
| `bool` / 各宽度整数 / 指针 / `float32` / `float64` | **8** | 8 |
| `complex64` | **8** | 8 |
| `complex128` | **16** | 8 |
| 数组 / struct | `size_of(typ)` **向上取 8 的倍数** | 8 |
| 零大小类型（`struct{}` / `[0]T`） | **0**（仍可算地址） | 8 |

- **`frame_size`** = `16`（`fp`/`lr`）+ 值槽区 + 取址槽区 + 临时区，**向上取 16 的倍数**。
- **`sub sp, sp, #(frame_size - 16)`**：因为 `stp x29, x30, [sp, #-16]!` 已经动了 16。
- **零值**：`slot_types` 里的槽进帧时清零（`str xzr` / 按 8 字节步长的 `memset`）；
  可提升的槽不建存储（M6 已把它们变成值）。
- **零大小类型**（`struct{}` / `[0]int`）：槽宽 **0**，但**仍然有地址** ——
  `&x` 合法，且 `zerosize.go` 要求 `new([0]int)` 两次拿到**同一个地址**
  （官方是 `runtime.zerobase`）。所以 `rt_arena_alloc(0)` 必须返回一个**固定哨兵**，
  零大小全局也必须落在同一个地址上；返回「每次不同的地址」会让 `zerosize.go` 直接 panic。

### 7.3 对象布局：**只消费，不自算**

`Field` 的偏移、`Index` 的元素宽度、聚合的 `size_of` **一律来自 `rgoc-types`**。
`rgoc-arm64` 里**不许**出现「按字段顺序自己加偏移」的代码 ——
两套布局一旦不一致，症状是「结构体第 2 个字段读到了第 3 个」，而小结构体的 fixture 仍可能全绿。

## 8. `FRAME-MAP v1`（M7 新增，**行语法冻结**）

### 8.1 行语法

```text
# FRAME-MAP v1
# func <name> frame=<n> slots=<n>
# slot <v> off=<n> size=<n> type=<t>
# safepoint b<k>:<idx> offs=[<n>,<n>] ptrs=[<n>]
```

- 头两行**固定顺序**，字段不可省。
- `slot` 行按 `ValueId` **升序**；`off` 是**相对 `fp` 的负偏移**（与 `add x, sp, #off` 的立即数一致）。
- `safepoint` 行按「块号升序、块内指令下标升序」；位点记法与 `SSA-LIVE v1` **完全相同**（入口写 `b<k>:-1`）。
- `offs` 是该位点活值的偏移列表（升序）；`ptrs` 只含**指针类型**的偏移。
- 空集写 `[]`，**不省略字段**（与 `C10` 的 `params=[]` 同口径）。

### 8.2 完整示例

```text
# FRAME-MAP v1
# func main frame=64 slots=7
# slot v0 off=-16 size=8 type=int
# slot v3 off=-32 size=16 type=complex128
# safepoint b1:0 offs=[-16,-32] ptrs=[]
```

### 8.3 三条实现决定

| # | 决定 | 理由 |
|---|---|---|
| 1 | 列表带方括号，空集写 `[]` | 与 `C10` 同口径；同一个仓里两套列表语法只会让人猜 |
| 2 | 块入口的定义点写 `b<k>:-1` | `-1` 比任何指令下标都小，排序天然正确，不必给 `Pos` 加枚举 |
| 3 | 聚合只报**起始偏移 + 大小**，不报内部指针 | M7 没有对象模型（M9c2 才有）；假装报了内部指针就是空话 |

## 9. 确定性（M7 新增，**冻结**）

`FRAME-MAP v1` 与生成的 `.s` 都必须**逐字节可复现**：

| 禁止 | 后果 |
|---|---|
| 地址 / 指针值 | 每次运行都不同 |
| `HashMap` 迭代序 | 同一输入两次输出不同（`T-NAT-48` 的反向守卫就是钉这个） |
| 时间戳 / 主机名 / 绝对路径 | 换机器就变 |
| 随机标签名 | 同上 |

**标签命名规则**：函数标签 `<name>`；字符串常量 `.Lstr<N>`（N 按**生成顺序**单调递增，不按内容哈希）。
