## 1. 目标平台（首发固定）

| 项 | 值 | 来源 |
|---|---|---|
| 目标三元组 | `aarch64-unknown-linux-gnu` | `03` §0.2 |
| 架构 | ARM aarch64（64 位 little-endian） | 实测 `file` 判定 |
| 寄存器宽度 | 64 位（`x0`–`x30`） | AAPCS64 |
| 产物 | ELF 64-bit LSB PIE | 实测 `file` 输出 |

**已验证**（`T-S3-02`）：产物 `file` 判定**同时**含 `ELF 64-bit LSB` **与** `ARM aarch64`。

> **为什么必须判两个条件**：x86-64 的 ELF 同样含 `ELF 64-bit LSB`。
> 只判那一个会漏掉「链接到了错误架构」—— 而那在跨平台机器上很容易发生。
> 有测试 `t_s3_02_*` 钉住**两个**条件都要断言。

## 2. 六项记录（`T-S3-04` 的逐条固化）

### 2.1 调用约定

**结论**：裸 `_start`，**不经 C 运行时**。系统调用参数走 `x0..x5`，
返回值在 `x0`，**系统调用号在 `x8`**，用 `svc #0` 陷入内核。

| 调用 | 号 | 参数 | 返回 |
|---|---|---|---|
| `write` | **64** | `x0`=fd，`x1`=buf，`x2`=count | `x0`=实际写入字节数 |
| `exit_group` | **94** | `x0`=状态码 | 不返回 |

**必须用 `exit_group`（94）而非 `exit`（60）**：多线程下 `exit` 只退出当前线程。

**未验证**（缺口）：只验证了「**无参、无返回**」的系统调用。
一旦有用户函数，以下**全部未验证**：参数传递、被调用方栈帧、
callee-saved 寄存器（`x19`–`x28`）的保存义务。**那是 M7 的内容。**

### 2.2 栈对齐

**结论**：本 fixture **完全不动栈** —— 没有 `push`、没有 `bl`、没有局部变量，
所以 `sp` 始终是进程入口时的值，**天然满足 16 字节对齐**。

**⚠️ 「不需要动栈」不等于「栈对齐已验证」**（有测试专门钉这句：`t_s3_04_栈对齐项不得声称已验证`）：

| 未验证 | 说明 |
|---|---|
| `bl` 前的 16 字节对齐 | AAPCS64 要求每次函数调用前 `sp` 保持 16 字节对齐 |
| leaf 函数不保存 `fp`/`lr` | 叶子函数可不保存链接寄存器 |
| 非 leaf 必须保存 | 非叶子函数**必须**保存 `fp`(x29) 与 `lr`(x30) |
| 栈帧大小向上取整 | 局部变量布局后 `sp` 仍须 16 字节对齐 |

**归属**：M7。

### 2.3 输出流

**结论**：走 `write(2)` 系统调用，`x0` = fd（**1 = stdout**、**2 = stderr**）。

**已验证**：
- `x1` 用 **`adrp` + `add :lo12:`** 取数据段地址 —— **PIE 下不能用绝对地址**（有测试钉住不得出现 `ldr x1, =`）
- fixture 声明 `Stream::Stdout` ⇒ 用 fd 1；`Stream::Stderr` ⇒ 用 fd 2（有测试钉住两者**不同**）

**⚠️ 已知缺口（代码里留了 `TODO(S3-04)` 标记）**：
**未处理 `write` 的部分写（短写）返回值。**
Linux 上 `write` 可能只写一部分，真实实现**必须循环**。
fixture 只有 6 字节，实践中不触发 —— 所以不能假装处理了。

**归属**：M7。

### 2.4 退出码

**结论**：`exit_group(2)`，`x0` = 状态码；正常结束写 **0**。

**已验证**：运行该 ELF 的退出码为 `0`（`T-S3-03`）。

**未验证**：非零退出码的路径；**Go 的 panic 退出码是 2**（与本条不同），
「什么情况下 rgoc 该用哪个」尚未决定 → **M5e**（panic/recover）。

### 2.5 最小 runtime 桥接

**结论**：**零 libc 符号** —— `svc #0` 直达内核，不需要任何库函数。
但链接产物**仍然是动态链接**（`readelf -d` 显示 `NEEDED libc.so.6`），
那是**链接器默认加的，我们一个符号都没引用**。

| 开关 | 状态 | 不加会怎样（实测） |
|---|---|---|
| `-nostartfiles` | **必需** | **链接失败**：`multiple definition of _start; /lib/aarch64-linux-gnu/Scrt1.o: first defined here` + `undefined reference to main` |
| `-Wl,-s` | **必需** | 链接成功但**产物不可复现**（见 §3） |
| `-static` | **故意不加** | 能链，但变成 static-pie 且体积更大；会掩盖「到底依赖了什么」 |

> `-nostartfiles` 的原因：C 运行时启动文件 `Scrt1.o` **已经定义了 `_start`**，
> 与我们手写的 `_start` 冲突。裸汇编程序必须显式去掉它。

**「不引用 libc 符号」不等于「不需要 libc」**（有测试专门钉这句）。
要真正静态还得加 `-static`，M0 故意不加。

**⚠️ `-Wl,-s` 的代价**：产物**没有符号表** ⇒ 对运行无影响，但**不可符号级调试**
（无函数名、无行号）。将来若要对生成物做符号级调试，
必须去掉 `-s` 并改用「按 section 比对」而非「整文件逐字节比对」。

**rgoc 真正的 runtime**（map / scheduler / GC）**完全未涉及** ——
`03` §M5 明确「宿主管理内存但仍监控运行预算」，那是 M5 起的事。

### 2.6 unwind 边界

**结论**：**不可 unwind**。生成的汇编**没有 `.cfi_*` 指令**，
链接产物也**没有 `.eh_frame` 段**。任何栈回溯（panic 打印调用栈、`backtrace(3)`）
都拿不到信息。

**这是当前形态的固有限制，不是待办**。要支持 unwind 就得在每条指令后维护
CFI 行号表并保证与 unwind 表同步 —— 那是**独立的一块工作**。

**写下来的理由**：将来有人加 `-fasynchronous-unwind-tables` 时，
要知道这是**新增能力**而非「本来就支持」。

**与 M5 的对齐问题**（待解决）：M5 的 panic 沿栈向上传播
与 M7 的 unwind 能力**是同一套机制还是两套**？M0 无法回答 ——
因为 M0 连 unwind 都没有。

## 3. 产物可复现性（`T-S3-05` 的实测结论）

**不加 `-Wl,-s` 时，同一份汇编重复链接三次，产物字节不一致**：

```text
$ for i in 1 2 3; do clang -nostartfiles -o out$i.elf hello.s; done
$ cmp out1.elf out2.elf
out1.elf out2.elf differ: char 66200, line 4
```

**定位链（三步，每步都必要）**：

1. **BuildID 三次完全相同**（`84a05590…`）—— BuildID 是**内容哈希**，
   相同即证明**代码内容本身可复现**；
2. **文件大小三次相同**（67384 字节）—— 排除「长度不同」这一类；
3. `readelf -p .strtab` 打出根因：

   ```text
   String dump of section '.strtab':
     [     1]  hello-d9450b.o     ← ★ 随机后缀
   ```

   那是 **clang 汇编器生成的中间目标文件名**，以 `STT_FILE` 符号留在符号表。

**处置**：加 `-Wl,-s` 后三次**逐字节相同**（66480 字节）且程序照常运行。

> **这不是为了让测试通过而放宽判定** ——
> 符号表对可执行文件的**运行**毫无作用；剥掉它反而让「结果一致」这条门禁
> **真正约束到 rgoc 自己的产物**上。

**对下游的约束**：M7 若要保留符号表（为了可调试），
则产物比对**必须改成按 section 比对**，不能整文件逐字节。

## 4. 对象布局 / 栈帧布局：**M0 完全未涉及**

| 主题 | M0 状态 | 归属 |
|---|---|---|
| **栈帧布局**（局部变量的偏移、对齐、溢出区） | ❌ 零局部变量 ⇒ **无布局可言** | M7 |
| **对象布局**（struct 字段偏移/对齐/填充、interface 值、slice 描述符、map） | ❌ 完全未涉及 | M5（值语义）/ M7（物理布局） |
| **参数传递**（超过 `x0`–`x7` 怎么办、栈上传参） | ❌ 只有 `write` 的 3 个参数 | M7 |
| **返回值**（多于一个返回值时怎么返回） | ❌ 未涉及 | M5b / M7 |
| **对齐规则**（各类型的对齐要求） | ❌ 未涉及 | M5 |

**为什么 M0 不猜这些**：布局规则的**每一个数字**都会在 M7 被大量引用，
而 M0 没有任何实测依据 —— 写下来的只会是「看起来合理」的猜测，
而**猜测被当成结论**正是 `03` §M4 的 M3「砍项」反复警告的事。

## 5. runtime symbol bridge：**M0 只验证了「不需要」**

M0 的结论是**否定的**，但这个否定本身有价值：

| 问题 | M0 的回答 |
|---|---|
| 最小可运行程序需要 runtime 吗？ | **不需要** —— `svc #0` 直达内核 |
| 需要 libc 吗？ | **不引用任何 libc 符号**（但产物仍动态链接） |
| 需要 scheduler 吗？ | **不需要**（单线程直线执行） |
| 需要 GC / 分配器吗？ | **不需要**（无堆分配，`hello` 在 `.data` 段） |

**它证明的是「后端路线可行」，不是「rgoc 的 runtime 已设计」**。
`03` §M5 明确：宿主管理内存但监控预算；M9 才有 Go 语义完整的 map/GC。
